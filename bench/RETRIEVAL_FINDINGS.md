# 檢索策略比較：為什麼加了規則層、為什麼沒有加 BM25

> 資料：`bench/retrieval-hard-*.json`，由 `bench/retrieval_eval.py` 產生。2026-09-12。
> 題庫：`golden/questions-hard.json`（18 可答 + 8 不可答）。只量檢索層，不跑生成。

## 起點：原本的基準集量不出任何差異

`golden/questions.json` 的 12 題可答題，稠密檢索拿到 **recall@5 = 1.000、MRR = 1.000、
top1 = 1.000**——連第一名都全中。README 早就自陳原因：那些題是「讀著條文寫出來的」，
用字與條文天然接近。**在天花板上做 A/B 是量不出東西的**，所以先補題庫再談改檢索。

`questions-hard.json` 分三組，刻意讓 dense 與詞彙匹配各自的強項分離：

| 組別 | 設計意圖 |
|---|---|
| colloquial（12 題） | 同樣的條文，改用一般人的講法問，避開所有法條詞彙。考 dense 的語義泛化。 |
| referential（6 題） | 指名法規名與條號提問。考精確匹配，也驗證 `ingest.py` 那個「把條號拼進被 embed 的文字」的設計到底有沒有效。 |
| unanswerable（8 題） | 原封搬過來當反向對照。召回變強時，近似題更容易把模型推向硬答——recall 上升但拒答退化不是進步。 |

## 三種策略的實測

| 策略 | colloquial recall@5 / top1 | referential recall@5 / MRR / top1 | 總體 recall@5 |
|---|---|---|---|
| `dense`（現況） | 0.917 / 0.583 | 0.667 / 0.833 / 0.500 | 0.833 |
| `hybrid`（rule+BM25+dense，RRF 均權） | **0.500 / 0.000** | 1.000 / 0.792 / 0.667 | 0.667 |
| **`rule+dense`（採用）** | **0.917 / 0.583** | **1.000 / 1.000 / 1.000** | **0.944** |

## 發現一：referential 是稠密檢索結構上的弱點，不是模型不夠好

純 dense 在指名條號的六題只有 recall@5 = 0.667，失敗模式高度一致：

    r01 問「銀行法第72-2條是在限制什麼？」→ 未進 top5，top1 是第22條
    r03 問「洗錢防制法第10條要求金融機構做什麼？」→ 未進 top5，top1 是第5條
    r05 問「個資法第11條在講什麼？」→ 第3名，top1 是第2條

**條號是符號，不是語義。**「第10條」與「第5條」在向量空間裡極近，因為它們語義上
都是「某條法規」。換更大的 embedding 模型不會改變這件事——這是稠密表示法的固有限制。

順帶回答了一個懸而未決的問題：`src/ingest.py` 把法規名與條號拼進被 embed 的文字，
註解寫著這是為了讓指名查詢「在向量空間也對得上」。**量了才知道那個設計沒有達成目的**——
它讓條號進入了向量，但向量本來就分不清數字之間的差異。意圖是對的，手段無效。

## 發現二：加 BM25 讓 referential 變好，但把 colloquial 弄壞了

三路均權 RRF 的結果是一組典型的「拆東牆補西牆」：referential 的 recall 升到 1.000，
但 colloquial 從 0.917 崩到 **0.500**，top1 直接歸零（12 題沒有一題排第一）。

原因不難理解：口語問句裡「到底」「生意」「幹嘛」這類詞的 character bigram
會匹配到大量不相關條文，而 RRF 均權讓這些噪聲與 dense 的正確結果平起平坐，
把原本排第一的答案擠下去。

**如果只看總體 recall（0.833 → 0.667），會知道它變差了但不知道為什麼；
分組看才看得到是「一組大好、一組大壞」。** 這就是不能只報平均數的實例。

## 發現三：規則層是零副作用的，因為它會自動退場

`rule+dense` 在 referential 拿到 recall / MRR / top1 全 1.000，**而 colloquial 的數字
與純 dense 一模一樣**（0.917 / 0.761 / 0.583）。

原因是條號規則在問句不含「第X條」時回空清單，融合層只剩 dense 一路，
行為完全等同原本的檢索。**它在不該生效的時候不生效**——這是規則層相對於
BM25 的結構性優勢：BM25 對每個查詢都會給出分數，想不干擾也不行。

這也正好是分層路由的教科書形狀：確定性強、邊界清晰的信號交給規則；
邊界模糊的交給語義。規則層便宜、可審計、命中即最高分；沒命中就閉嘴。

## 發現四：向量空間給不出「查無」信號

不可答題的 top1 距離中位數 0.4096、最近 0.2473；可答題的 top1 距離落在 0.30–0.43。
**兩者完全重疊**，代表無法用距離閾值來判斷「這題語料裡沒有答案」。

這件事的意義：本專案 `false_answer_rate = 0` 的成績，**檢索端一分沒出**——
拒答完全靠生成端的 prompt 約束與引文閘。README 原本就寫了「這個數字不能全記在
閘門頭上」（因為本機模型偏保守），現在可以補一句更精確的：檢索端也幫不上忙。

## 採用與未採用

- **採用**：條號規則層，已合併進 `src/rag.py` 的 `retrieve()`（`_cited_articles`）。
  既有 11 個測試全數通過，另補守門測試釘住行為。
- **未採用**：BM25 三路融合。理由如上——它的收益在規則層已經拿到，代價卻是
  口語查詢的大幅退化。若未來要重新評估，該先解決中文切詞（bigram 噪聲太大），
  而不是調 RRF 權重。
- **未嘗試**：bge-m3 的原生 sparse 與 ColBERT 多向量。Ollama 的 `/api/embed` 只回
  稠密向量，要取另外兩種得改走 FlagEmbedding（安裝中，依賴解析耗時超過本輪預算）。
  值得做，但要注意：它面對的是與 BM25 同一個問題——**在口語查詢上詞彙訊號是噪聲**，
  所以預期它也需要條件式啟用，而不是無腦融合。

## 下一步：數據說該做 reranker，不是 sparse

直覺上的下一步是把 bge-m3 剩下兩種能力（sparse 詞彙權重、ColBERT 多向量）接上，
畢竟模型本來就支援。但看瓶頸在哪，優先序是反過來的。

採用規則層之後，剩下的改善空間幾乎全在 colloquial 組：

    colloquial   recall@5 = 0.917   top1 = 0.583
    referential  recall@5 = 1.000   top1 = 1.000   ← 已無空間

**colloquial 的 recall 與 top1 差距很大（0.917 vs 0.583），意思是正確答案大多有進 top5、
只是沒排在第一。** 逐題看更清楚：c02 排第 5、c08 排第 3、c11 排第 2、c12 排第 3，
只有 c03 是真的沒召回。

- **這是排序問題，不是召回問題。** sparse 與 hybrid 解的是「撈不撈得到」，
  對已經撈到但排錯的那四題沒有幫助——而且 BM25 那次的實驗顯示，
  詞彙訊號在口語查詢上是噪聲，接上去反而讓排序更糟。
- **reranker（cross-encoder）才對得上這個瓶頸**：它把 query 與每個候選放在一起
  深度比對，正是用來修 top-k 內部順序的。官方也建議 bge-m3 搭配 bge-reranker。
- 唯一能被 sparse 救的是 c03（完全未召回），一題。而 rerank 有機會動的是四題。

所以優先序是 **reranker > sparse**，理由是量出來的瓶頸位置，不是「模型有幾種功能就都要用」。
sparse 仍值得測，但它要回答的問題是「能不能在不傷口語組的前提下把 c03 撈回來」，
而不是「hybrid 是不是比較好」——後者這輪已經有答案了。

> **這個預測後來被驗證了（實測二）。** cross-encoder 動到的正是上面點名的那四題：
> c02、c11、c12 從第 5／2／3 名升到第 1，c08 從第 3 升到第 2；連原本判給 sparse 的
> c03 也被從第 7 名提到第 3 名。**瓶頸定位正確，處方也正確。**
> 附帶結果是 sparse 的必要性又降低了一級——它原本唯一的理由就是救 c03，
> 而 c03 已經被 reranker 救起來了。

### 實測一：LLM listwise 重排——零收益，100 倍成本

先用**手邊就有的** qwen3.5:4b 做 listwise 重排（pool=10 → top5），
目的是在付出專用模型的安裝與記憶體成本之前，先確認重排這個方向有沒有收益。

| | colloquial recall@5 | MRR | top1 | 耗時 |
|---|---:|---:|---:|---:|
| `rule+dense` | 0.917 | 0.761 | 0.583 | 2.0 s |
| `rule+dense` + LLM 重排 | 0.917 | **0.761** | **0.583** | **210.3 s** |

三個指標一模一樣，時間多了 100 倍。但**平均數相同不代表什麼都沒發生**——逐題看是零和：

    c11  第 2 名 → 第 1 名   改善
    c01  第 1 名 → 第 2 名   退化
    其餘不變

一題排對、一題排錯，剛好抵消。這比「完全沒有變化」更值得警惕：
模型確實在做判斷，只是判斷的品質與向量相似度**不相上下**，於是收益被自己的錯誤吃掉。

**結論與其邊界**：已證明的是「qwen3.5:4b 做 listwise 重排在這個任務上沒有淨收益」；
**沒有**證明「重排這個方向無效」——reranker 的品質差異很大，通用生成模型當評分者
本來就不是為此訓練的。專用 cross-encoder（bge-reranker-v2-m3，568M，是 bge-m3 的
官方配對）仍值得測，它要回答的問題是：**專門訓練過的相關性判別，能不能贏過
向量相似度？** 這一題 LLM 版沒有答案。

實作上刻意做的一件事：重排失敗（非法 JSON、編號缺漏或超範圍、逾時）一律退回原順序，
不做「盡量修補」。**重排是優化不是必要步驟**，它壞掉時系統該退回沒有它的樣子；
修補則會把模型的部分幻覺當成有效排序用下去。

### 實測二：cross-encoder 重排——第一個有淨增益的改動，但它會弄壞原本對的題

上一節留下的問題有答案了：**專門訓練過的相關性判別確實贏得過向量相似度。**
用 bge-reranker-v2-m3（568M，bge-m3 的官方配對，fp16 跑在 MPS 上）重跑同一組題：

| | colloquial recall@5 | MRR | top1 | referential | 耗時 |
|---|---:|---:|---:|:---:|---:|
| `rule+dense`（基準） | 0.917 | 0.761 | 0.583 | 1.000 | 2.0 s |
| 　+ pool=10、不重排（控制組） | 0.917 | 0.761 | 0.583 | 1.000 | 2.0 s |
| 　+ LLM listwise 重排 | 0.917 | 0.761 | 0.583 | 1.000 | 210.3 s |
| 　**+ cross-encoder 重排** | **1.000** | **0.819** | **0.667** | 1.000 | 214.9 s |

**先釘死歸因，再談增益。** 重排是在放寬過的候選池（pool=10）上做的，
所以「池子變大」本身就可能是增益來源——這是必須排除的混淆，而且不能靠推理排除。
控制組就是為此跑的：只放寬到 pool=10、不重排，三個指標一個都沒動。
**增益全部來自 cross-encoder，不是來自多撈了五條。**

跑了兩次，214.9 s 與 213.7 s、指標逐位相同，不是單次僥倖。

**逐題看才知道發生了什麼——這次不是零和，但也不是白吃的午餐：**

    c02  第 5 名 → 第 1 名   改善
    c11  第 2 名 → 第 1 名   改善
    c12  第 3 名 → 第 1 名   改善
    c03  未召回（第 7）→ 第 3 名   改善（recall@5 由此從 0.917 變 1.000）
    c08  第 3 名 → 第 2 名   改善
    c07  第 1 名 → 第 2 名   退化
    c10  第 1 名 → 第 2 名   退化

五題改善、兩題退化。這比看總分誠實得多：**這個模型不是「比較準」，是「對得多、錯得少」**，
淨值為正，但它確實會把原本排第一的答案擠下去。要不要接受這個交換，取決於下游能不能
容忍 top1 偶爾換人——在這個系統裡可以，因為引文閘是逐條查核的，
第 2 名進了 top5 仍然會被驗證到。換到一個只取 top1 餵給生成端的系統，這個交換就不划算。

**樣本邊界先講**：colloquial 只有 12 題，所以 recall@5 的 0.917→1.000 是**一題**、
top1 的 0.583→0.667 也是**一題**。單看這兩個數字，落在 12 題一題的噪聲量級裡，
不足以宣稱百分比的精確度。真正撐住結論的是**逐題方向一致**（五升二降、
且升的幅度較大），不是總分漂亮——這正是前一輪學到的「平均數沒變不代表什麼都沒發生」
反過來用：平均數變好也不代表真的變好，要看是誰在動。

**c03 值得單獨講，因為它推翻了一個先前裁決的依據。** 2026-09-12 的換模型提案
（見下方「決策：不換 embedding 模型」）之所以被否決，關鍵實查是「唯一失敗的 c03
其實只是被 k=5 截掉，正確答案排第 7，k 放寬到 7 就是 1.000」。那個實查沒有錯，
但它只說明了「這題不是模型爛」；cross-encoder 現在把同一題從第 7 名提到**第 3 名**，
做到的是放寬 k 做不到的事——**把正確答案往上排，而不是把切線往後挪**。
兩者在 recall@5 上都能得到 1.000，只有前者改善了排序品質。
這是 recall 單獨看會騙人的又一個實例，也是當初的否決結論該被修訂的地方：
否決「換 embedding 模型」仍然成立，但「這題已經沒有改善空間」不成立。

**成本要照實說**：214.9 秒對 2.0 秒，約 107 倍，與 LLM 版同一個量級——
差別只在這次換到了東西。這個延遲對批次評估可接受，**對線上互動不可接受**。
要上線得走條件式啟用（簡單查詢直接走向量、複雜的才開重排），
而「什麼叫複雜」本身還需要一個判斷器，那是另一個還沒做的題目。
**所以這一輪的處置是：結論入庫，暫不併進 `src/rag.py` 的生產路徑。**

> **2026-09-15 補記：上面的 214.9 s 量錯了對象。** `retrieval_eval.py` 的計時器包住整個
> 迴圈，而 `cross_rerank._load()` 是延後載入——第一題進來才開始讀 2.27 GB 權重、
> 轉 fp16、上 MPS，冷啟動全算進「26 題耗時」裡。單獨量重排本身（模型已載入、
> 先跑一次暖機、pool=10、M1 MPS）：
>
> | 候選條文長度 | 每題中位 | p95 | 26 題合計 |
> |---|---:|---:|---:|
> | ≈170 字（語料中位 100 字） | 1.19 s | 1.30 s | 31.5 s |
> | ≈570 字（語料 p90 384 字、最長 979） | 3.57 s | 3.74 s | 93.2 s |
>
> 模型載入 8 s（磁碟已有快取）。所以線上穩態是**每題 1–4 秒，不是「107 倍」**——
> 那個倍數有一半以上是冷啟動。這不推翻「批次可接受、互動要斟酌」的方向，但把問題
> 從「需要一個判斷器決定誰該重排」改成「1–4 秒對這個系統的用途能不能接受」，
> 後者是產品裁決不是工程題。若要把最壞情況壓平，候選文字截到 400 字即可
> （p90 以上才會被截），不必先做判斷器。量測腳本見 commit 訊息。

## 端到端驗證：加了規則層之後，生成端沒有退化

改 `retrieve()` 是動生產程式碼，光看檢索層指標不夠——必須確認多塞進來的條文
不會讓生成端出事（例如模型看到更多條文反而更敢硬答）。跑完整 `src/evaluate.py`：

| 指標 | baseline（git `f5c7e58`） | 加規則層後 |
|---|---:|---:|
| `retrieval_recall_at_k` | 1.0 | 1.0 |
| `answered_rate` | 1.0 | 1.0 |
| `citation_precision` | 1.0 | 1.0 |
| `false_answer_rate` | 0.0 | 0.0 |
| `elapsed_sec` | 738.1 | 548.1 |

四項指標全數維持，8 題不可答題仍全部走 `NO_CITATION` 拒答——**規則層沒有把
更多看似相關的條文塞給模型、進而誘發硬答**，這是改檢索時最該擔心的副作用。

**時間從 738 秒掉到 548 秒（−26%）不可歸因於本次改動。** 規則層只多一次 SQL 查詢，
理論上應該略慢而非快 190 秒。真正的差別幾乎確定是機器狀態：這次跑之前剛做完
推理量測，Ollama 的模型已經暖機常駐（`keep_alive`），baseline 那次很可能含冷啟動。
**兩次跑的環境不同，這個欄位就不該拿來比**——寫在這裡是為了防止日後有人
把它讀成「規則層讓系統變快了」。

> 操作上踩到一個坑並已修正：`evaluate.py` 會直接覆寫 `golden/results.json`，
> 跑之前沒備份。所幸該檔在 git 裡（`f5c7e58`），baseline 完好無損，已還原；
> 新結果另存為 `bench/results-e2e-after-rule.json`。**要比較前後就不能讓後者
> 覆蓋前者**——這是版控替評估紀律擋下的一次失誤。

## 決策：不換 embedding 模型（2026-09-12，三大指標自評）

**提案**：換成 nomic-embed-text-v2 或 Qwen3-Embedding，重建索引，看能不能把
`rule+dense` 的 0.944 再推高。**裁決：不做。** 以下是實查清單與逐項自評。

### 實查（不憑印象）

1. **0.944 的唯一失敗題是 c03**，而它不是「搜不到」——期望的銀行法第12條
   **排在第 7 名**（d=0.4080），第 6 名是 0.4075，**差距 0.0005**。
   第 5 到第 7 名全擠在 0.4062–0.4080 這個極窄區間。
2. **把 k 從 5 放寬到 7，recall 就是 1.000（18/18）**，k=10 亦同。
   **現有 bge-m3 的召回能力在這個語料上已經足夠**，問題出在截斷位置。
3. 真正剩下的瓶頸是 **top1 = 0.583**（排序），不是召回。
4. 評估集只有 18 題可答題，**一題等於 5.6%**。

### ① 完成率

提案的 DoD 是「recall > 0.944」。**這個 DoD 已經被一個常數改動零成本達成**
（k=5→7，recall 1.000）。更關鍵的是第二層問題：**即使換了模型且它真的更好，
我們也證明不了**——18 題的樣本量無法分辨兩個 embedding 模型的真實差異，
而 c03 的失敗本來就發生在 0.0005 的分數差距內，那是雜訊層級。

**沒有足夠的量測精度就換模型，等於拿感覺換感覺。** 這條線的價值一直建立在
「每個改動都有前後對照」上，換模型會是第一個無法被驗證的改動。**不及格。**

### ② 效率

成本不只是下載與重建索引（281 條）。**最大的是隱藏成本：換 embedding 等於
換向量空間，`dense` / `hybrid` / `rule+dense` / `+LLM rerank` 四組對照的數字
全部失去可比性，要全部重跑**，本文件的所有結論也一併作廢。

收益上限是 +1 題（0.056），而那一題已經被 k 的調整拿到了。**負報酬。**

### ③ 穩定性

這條線最有價值的產出不是 0.944 這個數字，是三個**負面結果**（BM25 有害、
LLM 重排零和、ingest 條號設計無效）與它們的診斷。換模型會讓這些全部失去依據。
更糟的是它立下一個壞先例：**「效果不夠好就換模型」——那是最貴、也最難驗證的
調整方式**，而且通常掩蓋真正的問題（這次真正的問題是 k 設太小與排序失準）。**退步。**

### 已有的前例支持這個裁決

LLM listwise 重排那次是零和的（c11 升、c01 降，淨值為零）。**那次教的就是：
在分數擠成一團的區間裡做調整，不會有淨收益，只會換個地方出錯。**
c03 的 0.0005 差距正是同一種區間——換模型很可能把 c03 換上來、把別題換下去。

### 建議的替代（按投報率）

1. **k = 5 → 7**。已完成端到端驗證，**沒有代價**：

   | 設定 | top_k | citation_precision | false_answer_rate | elapsed |
   |---|---:|---:|---:|---:|
   | baseline（git `f5c7e58`） | 5 | 1.0 | 0.0 | 738.1 |
   | ＋規則層 | 5 | 1.0 | 0.0 | 548.1 |
   | ＋規則層，k=7 | 7 | 1.0 | 0.0 | 647.2 |

   多兩條條文進 context 沒有讓引文精確率下降、也沒有誘發硬答，8 題不可答題仍全數拒答。
   檢索端則從 recall@5 0.944 變成 recall@7 1.000。

   **但結論要限縮**：端到端只在原本那 20 題（簡單題）上驗證過，難題集沒有生成端的
   標準答案可比。而且 MRR 從 0.761 降到 0.709——**召回變好、排序變差**，
   因為新進來的那兩席是排在後面的。真正要解決 top1 的仍然是重排，不是放寬 k。
   為此已把 `TOP_K` 改成可由 `RAG_TOP_K` 覆寫，預設仍是 5（改預設值要等重排的結論一起決定）。

   > 操作教訓（同一個坑踩了兩次）：`evaluate.py` 每次都會覆寫 `golden/results.json`，
   > 兩輪驗證都是跑完才想到要備份。兩次都靠 git 還原。**要比較前後就不能讓後者
   > 覆蓋前者**——這件事該由腳本保證，不是靠人記得。
2. **bge-reranker-v2-m3**。它對得上真正的瓶頸（top1 = 0.583 的排序問題），
   而且是本輪唯一還沒有答案的問題：**專門訓練過的相關性判別，能不能贏過向量相似度？**
3. **擴充評估集**。若日後真的要比較 embedding 模型，這是**前置條件而非配套**——
   沒有足以分辨差異的評估能力，換模型的結論不可信。而且擴評估集本身比換模型更有價值：
   它讓之後每一個決策都能被驗證，包括那些現在還看不出來的。

### 重新評估的觸發條件

任一成立就重開此決策：①評估集擴充到能穩定分辨 5% 以下的差異；②語料從法規換成
其他領域（本結論綁定「一條一塊、有明確條號」的語料特性）；③出現 recall 本身
真的不足的證據（不是排序問題）。

## 這組量測本身的邊界

- 18 題可答題（12 口語 + 6 條號），**樣本很小**；單題的成敗就會讓某組指標跳 0.083 以上。
  能支持的結論是方向（哪個策略在哪一組明顯較好），不是精確的百分比。
- 口語改寫是我（出題者）寫的，不是真實使用者查詢。**它比原題庫難，但不等於真實分布**。
- 只量檢索層。加了規則層之後端到端的 `citation_precision` 與 `false_answer_rate`
  是否維持，要另外跑 `src/evaluate.py` 驗證。

## 重跑

```bash
cd ~/rag-citation-gate
./.venv/bin/python bench/retrieval_eval.py --strategy dense      --questions golden/questions-hard.json
./.venv/bin/python bench/retrieval_eval.py --strategy rule+dense --questions golden/questions-hard.json
./.venv/bin/python bench/retrieval_eval.py --strategy hybrid     --questions golden/questions-hard.json

# 重排兩路（需要 .venv-hybrid，裡面才有 FlagEmbedding 與 torch）
./.venv-hybrid/bin/python bench/retrieval_eval.py --strategy rule+dense --rerank llm   --pool 10
./.venv-hybrid/bin/python bench/retrieval_eval.py --strategy rule+dense --rerank cross --pool 10 \
    --out bench/retrieval-hard-rerank-cross.json
# 歸因用的控制組：只放寬候選池、不重排，應該與基準完全相同
./.venv-hybrid/bin/python bench/retrieval_eval.py --strategy rule+dense --rerank none  --pool 10
```

> **環境備忘**：重排那兩路**不能用 `.venv`**，FlagEmbedding 與 torch 只裝在 `.venv-hybrid`。
> 用錯直譯器的症狀是 `ModuleNotFoundError`，很明顯；但同一個坑在下載模型時會偽裝成
> 別的樣子——我用錯直譯器跑 `snapshot_download`，它什麼都沒抓就結束了。
>
> **下載 bge-reranker-v2-m3（2.27 GB）踩到的坑，記下來免得重蹈**：
> 同時起兩個行程抓同一個模型會互搶檔案鎖，兩邊都掛在那裡、檔案長時間零成長，
> 看起來像網路慢而不像當掉。判斷方法是**隔 20 秒比兩次 `stat -f '%z'`**，
> 零成長就是卡住，不是慢。清掉重來又會浪費已下載的部分（`.incomplete` 換了檔名
> 就不會續傳）。最後是自己用 HTTP Range 接著既有的 `.incomplete` 下載、
> 再比對檔名裡的 sha256 驗證完整性——**HF 的 blob 檔名就是該檔的 sha256，
> 可以直接拿來當校驗碼**，這比相信下載器說「完成了」可靠。
